# 节奏与汇报(2026-08-29 用户连续三次反馈)

原话:「你怎么老是这么着急,你先委托两个 agent 进入容器执行个任务,跑个最简单 add 测试」
、「说了一堆没看懂,跑通了吗,怎么跑通的?」、「我刚才提的报告,路径 ip 容器名,命令等,还没有」。

## 节奏:先把最小的东西真跑一遍
- 设计/沉淀流程时,不要一路往下推到"下一阶段"。**方案还没被最小实证验证过,就不许继续往前铺。**
  用户反复把我拉回来的动作是:"先派两个 agent 跑个最简 add"。
- 最小实证的价值不是"证明能跑",而是**暴露第一跳的坑**(试点里就是 `conda activate` 缺失导致的
  `ModuleNotFoundError`)——不跑它,后面 200+ 用例会整片栽在同一行上。
- 每次答完不要急着宣布"下一步我去做 X"就真去做 X;用户经常先要看这一步的实证结果。

## 汇报:先给结论,再给链路
- **第一句必须是"跑通了 / 没跑通"这类直给结论**,然后用 3-5 行讲清"怎么跑通的"(一条链 +
  关键几步),再讲坑。不要用大段设计论述、表格、提交号开头 —— 用户会直接说"说了一堆没看懂"。
- **用户要的数据必须摊在回复里**,不能只说"写在 handback 文件里了"。
  ip / hostname / 容器名 / 工作目录 / 命令 / 结果 摆成一张小表贴出来;文件路径是补充,不是交付。
  (2026-08-29:两份 handback 早就在磁盘上,但我只讲结论不给汇总,用户等于没拿到报告。)
- 交付里主动标出**缺口/未取证**的部分,不要用"整体成功"盖过去。


## 路径一律给绝对路径(2026-08-30 用户反馈)

用户看到 `runs/20260830-2153-node41-parallel2/` 时问「这个完整目录是什么,最好放到当前的工作目录」
—— 它其实**已经在**工作目录下,是我只写了相对路径导致看不出位置。

规则:**汇报里出现的任何路径都写绝对路径**(或至少显式带上工作目录前缀)。
相对路径对我是清楚的(我知道自己的 cwd),对用户是悬空的 —— 他要判断"这东西在哪、要不要挪"。
远端路径同理:标明是哪台机、哪个容器内的路径。
