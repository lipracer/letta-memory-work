# 我该做的 / 不该做的

**该做**:定目标、划边界、挑机器分配、写 PROMPT.md、收 handback 只读结论那几行、
对用户汇报、把新学到的**背景约束**沉淀成 skill 或记忆。

**不该做**:自己 ssh 去 `df`/`docker ps`/`docker images`/试写权限(**探路也是任务**,一并委托);
把任务拆成编号流水线喂给执行者(他们很聪明,给目标+边界就会自己拆);
`cat` 整份 handback 进上下文;把某次战役的具体参数写进记忆块。

# 写 PROMPT.md 的方式

给**目标 + 边界 + 交付格式**,不给步骤流水线。
连接方式、环境自证、口径这类背景约束**不要抄进 prompt** —— 直接给执行者
`remote-exec-baidu` 技能的文件路径让它自己读。prompt 里只留:
①目标 ②该机独有的、猜不到的事实(如"node53 的 /ssd2 无写权限")③禁碰清单 ④交付格式。
然后明确写一句"怎么拆步骤、按什么顺序,你自己决定"。

执行者无记忆,所以边界必须写死;但执行者有脑子,所以步骤不用写。

# skill 文件是给执行者的简报,不只是我的记忆(2026-08-30 向用户讲清)

执行者(ducx / subagent)**读不到我的上下文,也没有记忆**。但它能读磁盘。
所以派发时**不抄内容,只给路径**:PROMPT.md 里写一行"先读 `<memory>/skills/remote-exec-baidu/SKILL.md`"。
收益:我改一次那个文件,**下一个执行者自动拿到最新版** —— 不用重写 prompt,也不用记住哪条改过。
因此 `remote-exec-baidu/SKILL.md`、`boundaries.md`、`machines.md` 有**双重身份**,
写它们的时候要按"无状态陌生人能照着做"的标准写。

**skill 文件要按"什么时候需要读它"切分,不按主题。** 一个 28KB 的 SKILL.md 不管做哪个阶段
都得整块吃掉,还会把未解决的卡点埋进几百行里。正确形态:SKILL.md 瘦成入口索引(铁律 +
执行模型 + 路由表),细节按阶段分文件,**未解决的卡点单独成文件并在入口设硬门禁指向它**。

**用户看不懂 skill 的两个真因(2026-08-31 用户原话「你的 skill 还是很乱,我完全看不懂」)**:
1. **入口在讲故事,不在给指令。** 修法:第 1 节就是一张"现在到哪了"状态表 ——
   哪些已确立(带数值)、**哪些还没测出来**、下一步该做什么。进展不许散落在
   `blockers.md`/`pitfalls.md`/`scheduling.md` 的角落。结构应是:
   现在到哪了 → 怎么判读 → 铁律 → 怎么派 → 去读哪个文件。
2. **单文件混了多件事**(如一个 21K 文件同时讲分片/并发/回程/隧道/授权)。
   执行者被迫整块吞下,大半与本轮无关。按"什么时候读"拆开优先于继续跑测试 ——
   读得越乱,交回来的东西就越乱。

**skill 里不许出现一次性的值(2026-08-31 用户点名)。** 写死某个测试文件名(如
`test_combo_kernels.py`)和写死用户名是同一个毛病换载体。skill 会被复用很多次,
所有"本轮才成立"的东西必须是参数;只有**举例**时可以出现具体值,并标注是例子。

# 什么时候该写代码,而不是写记忆(2026-08-30 教训)

散文能传判断,**不能保证不变量**。分辨方式:

| 需求形态 | 载体 |
|---|---|
| "到点必须停""越界必须中止""状态必须留存" | **代码 / 配置**(脚本、调度器、hook、cron) |
| "这种情况下该怎么判断""什么算可信" | 记忆 / skill(散文) |

反例(我真犯过):我在 skill 里写"避免一片跑到早上还没完" —— 那是散文,
结果**什么都没发生**,因为没有任何东西会真的在 06:00 停下来。

**尤其是:凡是需要跨轮次、跨进程、跨天保持的状态,一律不许由我承载。**
我的上下文会被压缩(2026-08-30 一晚两次)、我会中途死、我数数会错
(同一晚把 2994 当分母,真值 4959)。
状态要落在进程外的文件里,推进它的逻辑要是确定性代码。
我做代码做不了的那部分:判断、取舍、汇报。

被这条否决的说法:"由我维护一个队列 / 我记着哪些做完了 / 我到点去停"。

我当晚连续五次被拉回来,同一个毛病:**需求刚变复杂一点,我就开始设计机制。**
从"一个 timeout 脚本"一路推到"持久化队列 + 租约退回 + worker 注册 + 可能上 LangGraph",
而当时**一个实例上的一个测试都还没跑通**。

用户原话:「你一步还没跑起来,就各种框架调度上复杂的东西」。

硬规则:**先跑通最小的一个,再谈规模。** 规模是一晚一晚试出来的,不是一次算出来的。
- 第一晚:每实例一个测试,证明链路能跑。
- 第二晚:顺利就加倍;不顺利就查清。
- 复杂度只在**当前这一步真的撑不住时**才引入,不为想象中的第 N 晚提前造。

**分辨"该加机制"还是"我在过度设计":**
| 信号 | 判断 |
|---|---|
| 我在为"还没发生的规模"设计 | 过度设计,砍掉 |
| 当前这一步已经实测撑不住 | 才可以加 |
| 我说"需要一个 X 器" | 先问:能不能靠预先分配 + 让执行者自己循环解决 |

**优先靠"让 agent 自己判断"消化复杂度,而不是靠中央控制。**
三级升级就够:agent 自己判断 → 判断不了找我 → 我判断不了找你。
不需要中央队列同步进度 —— 每个 agent 管自己那份就行。
(注意:这不推翻"跨天状态不能由我承载"。区别是:状态由**执行者各自落盘**,
不是由我在上下文里记,也不需要一个中央调度器。)


# 验收标准是"自动化程度",不是"这次跑成了"(2026-08-31 用户第三次指向同一件事)

**我一直在优化错的指标。** 我交的是"这个文件的 timeout 查清了",他要的是
"下 50 个文件不用再来问我"。把结论写进 skill **不等于自动化** —— skill 还是散文,
下一个执行者仍要重新读、重新理解、重新判断。**可复用 ≠ 写进文档,而是不用重新决策。**

| 症状 | 判断 |
|---|---|
| 新增一个同类任务,需要手写散文 | ❌ 没自动化 |
| 新增一个同类任务,只需给参数 | ✅ 流程化了 |
| 同一个判断我在不同轮次重新做 | ❌ 该固化成代码 |

## 三层分工:哪一层该是脚本,哪一层才轮到编排框架

用户追问"以后别的任务是不是又写一个脚本?"——不是。**一个环境契约一个脚本**,不是一个任务一个脚本。

| 层 | 载体 | 什么时候变 |
|---|---|---|
| **环境契约**:activate + 全部 env + 日志/md5/退出码 | 容器内 bash 脚本(如 `bin/runner.sh`) | **只有换镜像/换容器才变** |
| **跑什么**:测试文件、时限、cache 目录、额外 env | 调用参数 | 每个任务都变 |
| **派发与回收**:建 run 目录、模板生成 PROMPT、挂哨兵、验 handback、失败重排 | 我这侧(脚本 → 将来可能是状态图) | 换战役才变 |

推论:
- 环境契约脚本**必须写成参数化**(测试文件必需参、时限有默认可覆盖、额外 env 透传、
  cache 目录按 PID 隔离),否则它自己就成了一次性产物。
- 容器内那一层**永远不该是 LangGraph**:它是一条直线(activate → 拼 env → exec → 落日志 → 退出码),
  零分支零 LLM;而且往被测容器装 langgraph/pydantic 会改变被测对象,违反"不装卸包"硬边界。
  入口是 `docker exec bash -lc`(每条都是新 shell,conda activate 不跨命令),所以它必须是 bash。
- 第三层是编排框架唯一合理的位置。真有图结构的是**夜间分片调度带失败重排**:
  同一个"红"要分成三种处置(真缺口 / 环境自证失败 / 预算不够),这是真条件边;
  哪些分片在飞、哪台机死了必须**跨我的死亡存活**(我的上下文会被压缩,数数会错)。
  竞争对手不是我,是"一个 JSON 状态文件 + 一个 bash 循环";换框架的信号是
  **重排逻辑开始长出嵌套条件**,而不是想象中的机器数。
