# 精度验收标准

> 定位:验收三级 **功能 → 精度 → 性能**(用户 2026-08-31 明确)。
> 精度是中间那级,也是**最容易糊过去、也最容易冤枉后端**的一级。

## 三级优先级的含义

| 级 | 问题形态 | 不过关时 |
|---|---|---|
| **功能** | 跑不起来、报错、collect 失败、整片 skip | 精度性能都无意义,先修这个 |
| **精度** | 跑通了,但数值不对 | **比功能问题更危险** —— 它不报错,会静默污染训练结果 |
| **性能** | 数值对,但慢 | 可优化,不阻塞正确性 |

**为什么精度必须排在性能前面**:一个慢的正确实现可用,一个快的错误实现是负资产。
而且精度问题一旦流到业务侧,归因成本远高于性能问题(表现为 loss 不收敛,而非某个数字变大)。

## 核心原则:不要自己发明容差

**上游 PyTorch 测试自带容差体系,验收应当直接沿用,而不是另定一套阈值。**

理由:
1. 上游容差是针对每个 op、每个 dtype 长期调出来的,包含了大量我们不知道的数值分析;
2. 自定阈值 = 改测试适配后端,**违反"不许改测试"的验收口径**;
3. 自定阈值无法与其他后端对比,失去"和 GPU 比"的意义。

上游的容差入口(用它们,别绕过):
- `torch.testing.assert_close(actual, expected, rtol=, atol=)` —— 默认容差**按 dtype 查表**
- `torch.testing._comparison` 里的 dtype→(rtol, atol) 默认表
- OpInfo 里每个 op 的 `tolerance_override` / `DecorateInfo`
- inductor 测试常用的 `check_model` / `common` 封装(内含自己的 `atol/rtol`)

→ **验收标准的正确表述不是"误差 < X",而是"上游断言通过"。**
我们要做的是**记录哪些 op 需要放宽、放宽了多少、为什么**,而不是全局调松。

## bit 对齐:哪些能要求,哪些不能

用户问的核心问题。判据不是"算子重不重要",而是**这个算子的结果是否由标准唯一确定**。

### 可以要求 bit-exact(逐位相同)

| 类别 | 例子 | 理由 |
|---|---|---|
| IEEE-754 单次基本运算 | `add` `sub` `mul` `div` `sqrt` | IEEE-754 规定这些运算**必须**正确舍入 → 结果唯一 |
| 数据搬运 / 形变 | `copy` `view` `reshape` `permute` `cat` `slice` | 不做算术,只搬 bit |
| 逐元素比较与逻辑 | `eq` `gt` `logical_and` | 布尔结果无舍入 |
| 类型转换(有明确舍入规则) | fp32→fp16 (round-to-nearest-even) | 舍入模式确定 → 结果唯一 |
| 整数运算 | 所有 int 算术 | 无浮点舍入 |

**这些不对齐就是 bug,不是"精度问题"** —— 不允许用容差掩盖。

### 不能要求 bit-exact

| 类别 | 例子 | 为什么不可能对齐 |
|---|---|---|
| 归约(浮点加法不满足结合律) | `sum` `mean` `norm` `softmax` `layer_norm` | **求和顺序不同 → 结果必然不同**。split reduction / cooperative reduction / 不同 tile 大小都会改顺序 |
| 矩阵乘与卷积 | `matmul` `conv` `attention` | 累加顺序 + 是否用 MAC/MMA 单元 + 累加精度(fp32 累加 vs fp16 累加) |
| 超越函数 | `exp` `log` `sin` `tanh` `erf` `pow` | **IEEE-754 不要求正确舍入**,各家实现/查表/多项式逼近不同。GPU 上 fast-math 版本更是差一大截 |
| 融合改变了运算数 | FMA vs 分开的 mul+add | FMA 只舍入一次,分开舍入两次 → 天然不同(**这是 inductor 融合的正常结果**) |
| 含随机性 | `dropout` `randn` | RNG 实现不同 |
| 并行归约 + 原子加 | 部分 backward(如 dQ atomics) | 加法顺序由调度决定,**同一后端两次运行都可能不同** |
| 多后端选择 | autotune 选中不同变体 | 不同 kernel 不同累加顺序 —— **这是 autotune 的正常行为** |

⚠️ **特别注意最后两条与我们这条线直接相关**:
autotune 的职责就是在多个数值等价但 bit 不同的变体里选一个。
**要求 autotune 路径 bit-exact 等于要求它只有一个候选** —— 自相矛盾。

### 判据总结成一句话

> **该算子的输出是否被标准唯一确定?**
> 是 → 要求 bit-exact,不对齐即 bug。
> 否 → 用上游容差,并记录归约顺序/累加精度差异。

第二个辅助判据:**同一后端跑两次是否 bit-identical?**
若否(如 atomics),那连"自己和自己对齐"都做不到,更不能要求和 GPU 对齐 ——
这类只能做统计意义的验收。

## 按 dtype 分档

用户问"不同数据类型标准又怎么定"。关键认识:
**容差不该按经验拍,应按该 dtype 的机器精度(eps)推导。**

| dtype | 有效位(含隐含位) | eps 量级 | 说明 |
|---|---|---|---|
| fp64 | 53 | ~2.2e-16 | 容差最紧 |
| fp32 | 24 | ~1.2e-7 | 基准档 |
| tf32 | 11 (尾数10) | ~1e-3 | ⚠️ **陷阱**:声称 fp32 但精度接近 fp16。若 GPU 侧开了 tf32 而我们没开(或反之),对比会大面积失败 —— **先对齐开关再谈精度** |
| fp16 | 11 | ~1e-3 | 动态范围小,易溢出 |
| bf16 | 8 | ~8e-3 | 指数位同 fp32(不易溢出),但**尾数比 fp16 还少** → 容差要比 fp16 更松 |
| fp8 e4m3 / e5m2 | 4 / 3 | ~6e-2 / ~1e-1 | 逐元素比较意义很小,应看**分布/统计指标** |
| fp6 / fp4 | ≤3 | — | 同上,只能统计验收 |
| int / bool | — | 0 | **必须 bit-exact,无容差** |

### 由此得出的分档规则

1. **fp64 / fp32**:用上游默认容差,不放宽。放宽必须写明理由。
2. **bf16 容差要比 fp16 松**(尾数更少)—— 常见错误是给两者同一个阈值。
3. **低精度(fp8 及以下)不做逐元素比较**,改用:
   - 相对误差的**分位数**(如 p99 < X),不是 max
   - 余弦相似度 / 相对 L2 范数
   - 是否有 `inf` / `nan` 新增
4. **混合精度看累加精度,不看存储精度**:bf16 存储 + fp32 累加,容差应按 fp32 推;
   若我们的实现用 bf16 累加,那是**实现缺陷**,不是精度容差问题 —— 要立案为 gap。
5. **tf32 类开关必须先对齐**,否则测的是配置差异不是实现差异。

## 归入验收清单的方式

精度问题进缺口清单时,verdict 要能区分这三种(混在一起会做出错误的修复决策):

| verdict | 含义 | 处置 |
|---|---|---|
| `precision_bug` | 该 op 本应 bit-exact 却不对齐,或误差远超该 dtype eps 能解释的量级 | **真实缺口,排修复** |
| `precision_expected` | 归约顺序/FMA/超越函数导致,量级与 eps 相符 | 记录并豁免,**须写明是哪种机制** |
| `precision_config` | tf32/fast-math/累加精度等**开关不一致**导致 | 修配置后重测,不算 gap |

**判断"误差是否可被 eps 解释"的粗略办法**:
归约的误差随元素数 N 增长,量级约 `sqrt(N) * eps`(随机误差)到 `N * eps`(最坏)。
若观察到的相对误差远超 `N * eps`,那不是归约顺序问题,是真 bug。
→ 这给了一条**可判定**的界,而不是靠"看起来差得多不多"。

## 与性能线的关系

精度和性能在 autotune 这条线上是**耦合**的:
- autotune 选变体依据的是速度,但不同变体精度不同;
- 若验收只看速度,可能选中一个快但数值更差的 kernel;
- 所以 **autotune 的验收必须是"在通过精度断言的候选里选最快的"**,
  而不是"选最快的然后看精度过不过"。

→ 计划里性能指标必须附带"该配置下精度断言通过"的前置条件。
