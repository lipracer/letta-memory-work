## P2:定分片

分片依据按优先级:

1. **按硬件档位分** —— 这是硬约束,不是优化。H2(普通 GPU)、H3(CUTLASS SM90+ /
   Blackwell / CK / XPU)必须落到能跑的机器上,否则全是 skip 或 error。
2. **按子特性/测试文件分** —— 天然边界,失败时好定位。
3. **按 P1 耗时配平** —— 让每片时长接近。

### 调度模型:静态预分配 + 逐晚加倍(2026-08-30 用户定,第五次纠正)

**不要造调度器。不要引框架。不要动态队列、租约、worker 注册。**
这套东西我提过,被否了 —— 理由是**一步都还没跑起来就上复杂度**。

正确形态,简单到能一眼看完:

1. **筛池子**:找出今晚能用的机器实例。
2. **预先分配**:把测试**静态分给每个实例**。分完就定了,当晚不再调度。
3. **一实例一 agent**:每个实例配一个 agent,给它分到的测试,**让它自己循环跑**。
4. **第一晚保守**:每个实例**只派一个测试**。先看能不能跑起来。
5. **第二晚酌情加倍**:第一晚顺利,量翻倍;不顺利,查清再说。
6. 到 06:00 收工。没跑完的,下一晚继续。

为什么不需要调度器:
- **量是预先分好的**,不存在"谁先空出来派谁"这个问题 —— 没有派发决策,就不需要派发器。
- **每个 agent 自己循环**,进度由它自己管、自己落盘,不需要中央队列同步。
- **机器掉线不用租约退回**:它那份没跑完,下一晚重新分配即可。一晚的损失可接受。
- **加倍靠人判断,不靠算法**:每晚一个决策点(要不要加倍),由我提议、必要时你拍板。

**关于"agent 自己判断"的三级升级(用户明确):**

```
agent 遇到问题 → 自己能判断的,自己处理并记录
              → 判断不了 → 找我
              → 我判断不了 → 找你
```

这条很重要:**不要求 agent 遇事即停、也不要求它硬扛。** 它有自主判断权,
边界是"判断不了就上报",而不是"什么都上报"或"什么都自己扛"。
我同理:我判断不了就找你,不自己编一个解释糊过去。

**加倍的节奏是这套设计的核心**:规模不是一次算出来的,是**一晚一晚试出来的**。
所以第一晚的目标不是产出数据量,是**证明这条链能跑起来**。

### 回程通道:只能用文件信箱(2026-08-30 实测)

三级升级的第二级(「agent 判断不了 → 找我」)**需要一条回程通道**。实测结论:

**`ducx queue` 对 `ducx exec` 起的 session 无效,不能用。**
`ducx queue --thread <session id> --message "..."` 返回 `Queued message ...`(rc=0),
但消息**永远躺在 `~/.baidu-cx/queue_1.sqlite` 的 `queued_items` 表里不被消费** ——
观察 10+ 轮心跳(~150s)后该行仍在,executor 完全不知道有消息。
`queue` 是给**交互式 session**(`ducx resume`)用的,`exec` 非交互模式不轮询这张表。
⚠️ 副作用:塞进去的行不会自己消失,验证完要 `delete from queued_items where thread_id=...`,
否则污染下次同 thread 的交互式会话。

**所以派出去就是单向的:我不能中途跟它说话。** 唯一可行的双向方式是**文件信箱**:

| 方向 | 做法 |
|---|---|
| **agent → 我** | 判断不了时写 `<run_dir>/NEEDS_DECISION.md`(写清:卡在哪、它的两个候选、缺什么信息),然后**继续跑别的**或退出,不要空转等我 |
| **我 → agent** | 我写 `<run_dir>/DECISION.md`;agent 在循环每轮开头读一次,有就照办 |
| **我怎么知道** | 挂 Monitor 盯 `<run_dir>/NEEDS_DECISION.md` 出现。**run 目录是新建的,所以文件存在 ⟺ 本轮真求助** —— 判据就这么简单(复用目录才需要改名防残留,已废弃) |

这条要写进给执行者的 PROMPT:**"你判断不了,就写 NEEDS_DECISION.md,别硬扛也别空等。"**

Letta subagent 略好:可用 `conversation_id` 恢复对话追问,但那也只在**回合之间**,
执行中途同样插不进话。所以文件信箱是通用解,两种执行者都适用。

### 我在这套里做什么

| 谁 | 管什么 |
|---|---|
| **每个 agent(一实例一个)** | 拿到自己那份测试,循环跑,自己判断问题,判断不了上报 |
| **远端脚本 / 命令** | 单条不越界:`timeout`、日志落盘、标 `TRUNCATED` |
| **我** | 筛池子、静态分配、**定每晚加不加倍**、收上报、判断红是环境还是真 bug、汇报 |
| **你** | 我判断不了的时候拍板 |

**❌ 已作废的说法**(我提过,被否了,不要再提):
"由我维护一个待跑分片队列"、"按回收速度动态续投"、"租约到期自动退回"、
"需要一个持久化调度器 / LangGraph"。
真正的教训不是"该用框架",而是:**先把一个实例一个测试跑通,再谈规模**。

## 机器资源是借来的:窗口与硬性收工(2026-08-30 用户明确)

这些机器**白天是别人干活用的**。我们只在**夜间和周末**蹭空闲资源,所以窗口不是建议,是纪律。

### 窗口
| 时段 | 可用 |
|---|---|
| 工作日 夜间(**23:00** → 次日 **06:00**) | 可用 |
| 周末 全天 | 可用 |
| 工作日 其余时间(06:00 → 23:00) | **禁止铺开** |

⚠️ 工作日窗口只有 **7 小时**,不是 10 小时。**23:00 之前不许启动** ——
别人可能还在用机器,晚上早些时候占卡跟白天占卡一样是事故。

### 硬性收工:早 06:00 必停,跑没跑完都停
**到点强制结束,不允许"就快跑完了再等等"。** 白天占着卡影响别人干活,
比少拿一片数据严重得多。

实现方式(**两层,缺一不可**):
1. **每条测试命令自带 `timeout`**,时长按"距 06:00 还剩多少"算,不要写死一个大数。
   `timeout` 到点会杀掉 pytest,已跑完的用例结果仍在日志里。
2. **总闸看墙钟**:分片循环每跑完一片就查一次当前时间,
   `≥ 06:00` 就**不再启动下一片**,直接收尾写 handback。
   (只靠单条 timeout 不够:最后一片可能 05:59 才启动。)

收工时必须**保住已完成的部分**:handback 里写清
`跑完哪几片 / 哪片被强杀在哪个用例 / 哪几片压根没启动`。
**被截断的分片要标 `TRUNCATED`,不许当成 failed 统计**——
两者含义完全不同,混在一起会把"没跑"误读成"跑挂了"。

### 排期反推(P2 定分片时就要算)
工作日可用窗口 = **7 小时**(23:00→06:00)。这个数用来决定**分片切多小**
(小到能频繁回收、好续投),**不是用来决定"总量能不能一晚跑完"** ——
跑不完是常态,没跑完的下一晚继续,见上面「静态预分配 + 逐晚加倍」。
**不许为了"一晚跑完"去砍测试范围**,也不许靠"拖到白天"或"提前到 23:00 前"补。
周末窗口大得多,大批量优先排周末。

### 跨零点的 relay 指纹(2026-08-30 实证踩坑)
relay 指纹**按天失效**。2026-08-30 01:46 的 P1 基线就是这么断的:
`Connection timed out during banner exchange`,16 个文件全部 `UNAVAILABLE`。
**夜间战役必然跨零点**,所以这是整套流程的硬风险,不是偶发。
P3 铺开前必须先定跨天续认证的办法(候选:零点后再启动、睡前解锁看能否覆盖整夜、
查 relay 有无长效凭据),**没定就不许安排跨零点的无人值守任务**。


### 触发
用 `letta cron` 建定时任务(加载 `scheduling-tasks` 技能拿准确 flag,别背)。
一次战役用**一次性 cron**,不要建成 recurring——跑砸了会每晚重复烧机器。

### 委托
给每片起一个 subagent,**登录方式和执行纪律全部写进 runbook 文件**,不写进 prompt
(见 `RUNBOOK-template.md`)。prompt 里只说:cd 到哪、读哪个 runbook、负责哪个分片文件、交付什么格式。

这样做的理由:登录链路知识不该占我的上下文,而且下次换人换机器只改 runbook。

### 并发上限
**最多 2 路。** 2026-08-28 实测 4 路并行时本机堆了约 80 个 relay 长连接,
5 台出现 `Connection timed out during banner exchange`。relay 网关是共享瓶颈,
不同节点也会互相影响。

⚠️ **这条是整个「资源池」模型的真正上限,尚未解决(2026-08-30)。**
瓶颈**不在远端机器数量**,在**本机 → relay 网关**这一跳。
所以池子里有多少台可用是一回事,**我能同时驱动多少台是另一回事** ——
不要把"池子有 20 台能用"直接当成"能同时跑 20 路"。

出路的方向是**把"常驻连接数"和"在跑机器数"解耦**(均未验证):
①下发即断:`nohup` 启动远端脚本后立刻断开,机器在跑但不占连接;
只在**轮询状态时**才连,并发压到 ≤2 条 —— 这样在跑的机器数可以远大于连接数;
②状态用文件/网盘回收,而不是保持 ssh 长连接读 stdout;
③首批错开首连认证,避免同时首连。
**在这条解决之前,不许按"池子里所有机器同时铺开"设计 P3** —— 会整片断在 banner exchange。

### 长连接
`ControlMaster auto` + `ControlPersist 8h`,socket 在 `~/.ssh/sessions/`。
**relay 指纹认证是 per-host 的,N 台就是 N 次首连认证,省不掉**;
长连接省的是同一台机器上后续命令的重连(实测 12s+ → ~0.9s)。
夜间任务要注意 8h 窗口:凌晨建的连接白天可能已过期。

### 审计
每个执行者有**自己的 run 目录**,按 `HANDBACK-schema.md` 的布局
交付:`campaigns/<战役名>/runs/<时间戳>-<机器>-<任务>/{PROMPT.md, handback.md, run.log, 脚本, fetch.err}`。
**一次派发一个新目录,不复用**(隔离靠路径,见 `HANDBACK-schema.md`)。
主 agent 收齐后汇总 `campaigns/<战役名>/INDEX.md`,
**缺哪份要点出来**,不能用"整体成功"盖过去。
摘要级 run.log 要**拉回本机**并双端 md5 比对,让用户不必登机器就能翻。
用户要 review 每一条实际下发的远端命令 —— 这是硬要求,不是可选项。

### 早上的交付
`campaigns/<名字>/REPORT-<日期>.md`,必须包含:
- 与 P1 基线的 pass/fail 对比(**新增的 fail 是唯一真正重要的信息**)
- 每片实际耗时 vs 估算
- 环境搭建过程中的意外(缺包、拉镜像失败、盘满)
- 明确的下一步建议
