## P2:定分片

分片依据按优先级:

1. **按硬件档位分** —— 这是硬约束,不是优化。H2(普通 GPU)、H3(CUTLASS SM90+ /
   Blackwell / CK / XPU)必须落到能跑的机器上,否则全是 skip 或 error。
2. **按子特性/测试文件分** —— 天然边界,失败时好定位。
3. **按 P1 耗时配平** —— 让每片时长接近。

### 调度模型:静态预分配 + 逐晚加倍(2026-08-30 用户定,第五次纠正)

**不要造调度器。不要引框架。不要动态队列、租约、worker 注册。**
这套东西我提过,被否了 —— 理由是**一步都还没跑起来就上复杂度**。

正确形态,简单到能一眼看完:

1. **筛池子**:找出今晚能用的机器实例。
2. **预先分配**:把测试**静态分给每个实例**。分完就定了,当晚不再调度。
3. **一实例一 agent**:每个实例配一个 agent,给它分到的测试,**让它自己循环跑**。
4. **第一晚保守**:每个实例**只派一个测试**。先看能不能跑起来。
5. **第二晚酌情加倍**:第一晚顺利,量翻倍;不顺利,查清再说。
6. 到 06:00 收工。没跑完的,下一晚继续。

为什么不需要调度器:
- **量是预先分好的**,不存在"谁先空出来派谁"这个问题 —— 没有派发决策,就不需要派发器。
- **每个 agent 自己循环**,进度由它自己管、自己落盘,不需要中央队列同步。
- **机器掉线不用租约退回**:它那份没跑完,下一晚重新分配即可。一晚的损失可接受。
- **加倍靠人判断,不靠算法**:每晚一个决策点(要不要加倍),由我提议、必要时你拍板。

### 机内并行:先做礼貌的邻居,再做快(2026-08-30 用户交代)

用户交代:「发现机器上没有人用卡资源(这个可能有人在 benchmark),虽然我们用模拟器,
占了 CPU 可能也影响别人;如果机器资源空,我们可以开多进程最大化利用机器资源」。

**两个维度的并行,别混为一谈:**

| 维度 | 上限来自 | 现状 |
|---|---|---|
| **跨机并行**(N 台机器) | relay 网关连接数,**实测 4 路即断** | 硬上限,未解决 |
| **机内并行**(单机 M 进程) | 该机 CPU / 内存 / 别人的占用 | **完全没利用,这里有大量余量** |

关键认知:**机内并行不吃 relay 连接** —— 一条 ssh 进去,`docker exec` 里起 M 个进程,
relay 只算一条。所以**扩产能应优先往机内加,而不是往机器数加**。
这是绕过 relay 上限的正确方向(HTTP 隧道不是,隧道本身就是一条 ssh)。

**但机器是共享的,礼貌优先于速度:**
- 镜像默认跑**功能模拟器**,不用真卡 —— 但**吃 CPU 和内存**。
  「我们不用卡所以不影响别人」是**错的**:别人在 benchmark 时,我们抢满 CPU 会污染他的数据。
- 派 agent 前必须**先量该机的实际空闲**,而不是按标称核数算:
  `nproc`、`uptime` 的 load average、`free -g`、`top -bn1` 看谁在跑、`nvidia-smi`/XPU 工具看有没有人占卡。
  **有人在跑 benchmark(卡被占 / load 已高)→ 该机降级或跳过,不要挤进去。**
- 留余量,不要打满:**并行度按"空闲核数"算,并留出一部分给机器主人**。
  宁可少开两个进程,也不要成为那个把别人 benchmark 搞脏的人。
- 每个 agent 必须能**报出它实际用了多少并行度、以及当时的 load** —— 否则事后无法判断
  某片耗时异常是我们自己挤爆了,还是环境本身慢。

**并行怎么落地(不许造调度器,沿用静态预分配):**
- 容器**没有 pytest-xdist**,不要指望 `-n`。并行 = **同一容器内起 M 个独立 pytest 进程,
  各跑不同的测试文件**,输出写各自的日志。
- 文件级切分即可,不要拆到用例级 —— 简单、可复现、日志不混。
- ⚠️ **多进程共享 inductor/triton 编译缓存有互踩风险**:必须给每个进程独立的
  `TORCHINDUCTOR_CACHE_DIR` / `TRITON_CACHE_DIR`(各自子目录),否则缓存竞争会制造假 fail。
  这一条**没有实测过,第一次开多进程时必须专门验证**。
- 仍然是"一实例一 agent",只是**那个 agent 内部并行**;不需要中央协调。

**节奏(不许跳)**:第一晚**单进程**,只证明链路能跑;
先把 4 vs 13 那种不确定性清掉,再谈并行 —— 否则并行只会把不确定性乘以 M。
并行度也按"逐晚加倍"来试:1 → 2 → 4,每次看耗时是否线性下降、有没有新增 fail。
**如果并行后出现单进程没有的 fail,立刻退回单进程**并记录 —— 那是我们自己制造的假缺口,
会污染兼容性清单(见 SKILL.md 开头的大目标判读口径)。

**机器会越来越多**(用户明确会继续放资源)。所以池子的形态是:
机器数 × 机内并行度,两个都可调;**优先加机内并行度**(不吃 relay),
机器数受 relay 4 路限制,除非那条限制被解掉。

**关于"agent 自己判断"的三级升级(用户明确):**

```
agent 遇到问题 → 自己能判断的,自己处理并记录
              → 判断不了 → 找我
              → 我判断不了 → 找你
```

这条很重要:**不要求 agent 遇事即停、也不要求它硬扛。** 它有自主判断权,
边界是"判断不了就上报",而不是"什么都上报"或"什么都自己扛"。
我同理:我判断不了就找你,不自己编一个解释糊过去。

**加倍的节奏是这套设计的核心**:规模不是一次算出来的,是**一晚一晚试出来的**。
所以第一晚的目标不是产出数据量,是**证明这条链能跑起来**。

### 回程通道:只能用文件信箱(2026-08-30 实测)

三级升级的第二级(「agent 判断不了 → 找我」)**需要一条回程通道**。实测结论:

**`ducx queue` 对 `ducx exec` 起的 session 无效,不能用。**
`ducx queue --thread <session id> --message "..."` 返回 `Queued message ...`(rc=0),
但消息**永远躺在 `~/.baidu-cx/queue_1.sqlite` 的 `queued_items` 表里不被消费** ——
观察 10+ 轮心跳(~150s)后该行仍在,executor 完全不知道有消息。
`queue` 是给**交互式 session**(`ducx resume`)用的,`exec` 非交互模式不轮询这张表。
⚠️ 副作用:塞进去的行不会自己消失,验证完要 `delete from queued_items where thread_id=...`,
否则污染下次同 thread 的交互式会话。

**所以派出去就是单向的:我不能中途跟它说话。** 唯一可行的双向方式是**文件信箱**:

| 方向 | 做法 |
|---|---|
| **agent → 我** | 判断不了时写 `<run_dir>/NEEDS_DECISION.md`(写清:卡在哪、它的两个候选、缺什么信息),然后**继续跑别的**或退出,不要空转等我 |
| **我 → agent** | 我写 `<run_dir>/DECISION.md`;agent 在循环每轮开头读一次,有就照办 |
| **我怎么知道** | 挂 Monitor 盯 `<run_dir>/NEEDS_DECISION.md` 出现。**run 目录是新建的,所以文件存在 ⟺ 本轮真求助** —— 判据就这么简单(复用目录才需要改名防残留,已废弃) |

这条要写进给执行者的 PROMPT:**"你判断不了,就写 NEEDS_DECISION.md,别硬扛也别空等。"**

Letta subagent 略好:可用 `conversation_id` 恢复对话追问,但那也只在**回合之间**,
执行中途同样插不进话。所以文件信箱是通用解,两种执行者都适用。

### HTTP over ssh 隧道:双向通道可用(2026-08-30 实测)

**结论:容器内起 HTTP 服务,本机可双向读写 —— 但必须经 ssh 隧道,裸直连不通。**

| 路径 | 结果 |
|---|---|
| 本机 `curl http://10.206.192.139:28080/` 直连 | ❌ SYN 无回应,`Operation timed out` |
| 本机 ping 该 IP | ✅ 通(55ms)—— 所以**隔离在 TCP 端口级,不在 IP 级** |
| 本机 → 开发机放行端口 | **只有 80/443**(且那是网关,不是我们的服务);22/22222/8080/28080 全拦 |
| 宿主机自己 curl `10.206.192.139:28080` | ✅ 拿到 `HTTP_PROBE_OK` —— 服务和 host 网络模式都正常 |
| **经 `ssh -L` 隧道** | ✅ **GET 和 POST 都通**,POST body 正常落盘 |

用法:
```bash
ssh -f -N -L 28080:127.0.0.1:28080 devbox     # 建隧道(后台)
curl http://127.0.0.1:28080/probe.txt          # GET,~0.7s 往返
curl -X POST --data 'DECISION_TEXT' http://127.0.0.1:28080/   # POST,首次 ~1.4s
```
容器是 **host 网络模式**,容器内监听端口 = 宿主机端口,**不需要做任何映射**。

**这条通道的价值 —— 它是目前唯一验证过的双向通信方式**(`ducx queue` 已证不通):
- **agent → 我**:进度可 GET 轮询,不必等它跑完。
- **我 → agent**:决定可 POST 推进去,不必靠文件轮询。三级升级的第二级由此真正成立。

**但它没有解掉 relay 并发上限**:隧道本身就是一条 ssh 连接,N 台机器 = N 条隧道,
和直接开 ssh 是同一个瓶颈。⚠️ **不要以为"改用 HTTP"就能绕过 relay 限制。**
真要降并发,还是得靠"下发即断 + 少量轮询",而不是常驻 N 条隧道。

**取舍(第一晚不要上)**:每台机器要多起一个 HTTP 服务 + 一条隧道 + 端口分配 + 收尾 kill。
第一晚每实例只跑一个测试、跑完即回,**文件信箱够用,不要引入这套**。
等真需要"中途观察 / 中途干预"时再启用。

### 夜间无人值守:我替用户拍板的授权与边界(2026-08-30 用户明确授权)

用户原话:「半夜跑的话大概我睡了,所以你要尽量都能回答,你可以搜索你的整个记忆包括 git history
等,因为你的信息比 subagent 多,如果你回答不了,就退出吧,白天告诉我」。

**前提:我确实比执行者知道得多。** 执行者无记忆、只看一份 PROMPT;我有全部记忆、
skill 全文、`git -C "$MEMORY_DIR" log` 里的历次踩坑经过、recall 里的往轮对话。
所以执行者卡住时,**默认假设答案在我手上,先查再说"不知道"**。

收到 `NEEDS_DECISION.md` 后的固定动作(**顺序不许跳**):
1. 只读 `NEEDS_DECISION.md`(别 `cat` 整个目录)—— 它卡在哪、候选是什么、缺什么信息。
2. **查我自己的记忆**,按这个顺序:
   `grep -r` 本 skill 全部 md(`pitfalls.md` / `blockers.md` / `boundaries.md` / `machines.md`)
   → `git -C "$MEMORY_DIR" log --oneline` 和 `git log -p` 找当初为什么这么定
   → 必要时派 recall 子代理翻往轮对话。
   **绝大多数夜间卡点是白天已经解过的**(例:环境不闭环 = 漏 `TRITON_ENABLE_XCN_BACKEND=true`;
   用例整片 skip = 拿 `torch.xpu.is_available()` 当门禁)。
3. 拿定主意就写 `<run_dir>/DECISION.md`,给**可直接执行的命令或明确取舍**,不要给"你考虑一下"。

**能自己拍的**(有记忆依据、不越边界、可逆):
换端口/换目录名、调 pytest 参数、加环境变量、重跑取证、放弃某个用例继续跑其余、
选另一台已在池子里的机器、判定某个 fail 是已知基线内的。

**必须停下等白天的**(写 `MORNING-ESCALATION.md` 然后退出,不许自行放行):
要改仓库源码 / 要改容器或宿主机配置 / 要碰别人的目录或进程 / 要装卸包或换镜像 /
要动 `/klxlake` / 需要用户的业务判断(比如"这个 fail 算不算可接受") /
凭据或权限相关 / **任何我查完记忆仍然拿不准的事**。

**硬规则:拿不准就退出,不许猜。**
夜里瞎放行的代价是一整晚白跑 + 一份不可信的报告 —— 比"少跑一个用例、早上问一句"贵得多。
退出时必须留下 `MORNING-ESCALATION.md`:卡在哪、我查了什么、为什么不敢拍、
白天需要用户回答的**那一个具体问题**。早上第一句先报这个,别埋在报告里。

### 我在这套里做什么

| 谁 | 管什么 |
|---|---|
| **每个 agent(一实例一个)** | 拿到自己那份测试,循环跑,自己判断问题,判断不了上报 |

**❌ 已作废的说法**(我提过,被否了,不要再提):
"由我维护一个待跑分片队列"、"按回收速度动态续投"、"租约到期自动退回"、
"需要一个持久化调度器 / LangGraph"。
真正的教训不是"该用框架",而是:**先把一个实例一个测试跑通,再谈规模**。

## 机器资源是借来的:窗口与硬性收工(2026-08-30 用户明确)

这些机器**白天是别人干活用的**。我们只在**夜间和周末**蹭空闲资源,所以窗口不是建议,是纪律。

### 窗口
| 时段 | 可用 |
|---|---|
| 工作日 夜间(**23:00** → 次日 **06:00**) | 可用 |
| 周末 全天 | 可用 |
| 工作日 其余时间(06:00 → 23:00) | **禁止铺开** |

⚠️ 工作日窗口只有 **7 小时**,不是 10 小时。**23:00 之前不许启动** ——
别人可能还在用机器,晚上早些时候占卡跟白天占卡一样是事故。

### 硬性收工:早 06:00 必停,跑没跑完都停
**到点强制结束,不允许"就快跑完了再等等"。** 白天占着卡影响别人干活,
比少拿一片数据严重得多。

实现方式(**两层,缺一不可**):
1. **每条测试命令自带 `timeout`**,时长按"距 06:00 还剩多少"算,不要写死一个大数。
   `timeout` 到点会杀掉 pytest,已跑完的用例结果仍在日志里。
2. **总闸看墙钟**:分片循环每跑完一片就查一次当前时间,
   `≥ 06:00` 就**不再启动下一片**,直接收尾写 handback。
   (只靠单条 timeout 不够:最后一片可能 05:59 才启动。)

收工时必须**保住已完成的部分**:handback 里写清
`跑完哪几片 / 哪片被强杀在哪个用例 / 哪几片压根没启动`。
**被截断的分片要标 `TRUNCATED`,不许当成 failed 统计**——
两者含义完全不同,混在一起会把"没跑"误读成"跑挂了"。

### 排期反推(P2 定分片时就要算)
工作日可用窗口 = **7 小时**(23:00→06:00)。这个数用来决定**分片切多小**
(小到能频繁回收、好续投),**不是用来决定"总量能不能一晚跑完"** ——
跑不完是常态,没跑完的下一晚继续,见上面「静态预分配 + 逐晚加倍」。
**不许为了"一晚跑完"去砍测试范围**,也不许靠"拖到白天"或"提前到 23:00 前"补。
周末窗口大得多,大批量优先排周末。

### 跨零点的 relay 指纹(2026-08-30 实证踩坑)
relay 指纹**按天失效**。2026-08-30 01:46 的 P1 基线就是这么断的:
`Connection timed out during banner exchange`,16 个文件全部 `UNAVAILABLE`。
**夜间战役必然跨零点**,所以这是整套流程的硬风险,不是偶发。
P3 铺开前必须先定跨天续认证的办法(候选:零点后再启动、睡前解锁看能否覆盖整夜、
查 relay 有无长效凭据),**没定就不许安排跨零点的无人值守任务**。


### 触发
用 `letta cron` 建定时任务(加载 `scheduling-tasks` 技能拿准确 flag,别背)。
一次战役用**一次性 cron**,不要建成 recurring——跑砸了会每晚重复烧机器。

### 派发命令(2026-08-30 实测定型)

```bash
RUN_DIR=campaigns/<战役名>/runs/$(date +%Y%m%d-%H%M)-<机器>-<任务>
mkdir -p "$RUN_DIR"
nohup ducx exec -m gpt-5.6-terra \
  -c model_provider=oneapi -c model_reasoning_effort=high \
  --skip-git-repo-check -s danger-full-access \
  "$(cat "$RUN_DIR/PROMPT.md")" > "$RUN_DIR/ducx.log" 2>&1 &
```
**三个参数一个都不能省**(理由见 [[system/human/preferences/token-efficiency.md]]):
`-m` 挑模型、`model_provider=oneapi` 否则 fallback 到 openai 死循环重连、
`model_reasoning_effort=high` 否则被 config 里的 `low` 拖成低推理。
夜间战役用 **`gpt-5.6-terra`**(最强);轻量汇总用 `sol` 省额度。
`ducx.log` 是它的 stdout,**我不读**,只读它写的 `handback.md`。

### 委托
给每片起一个 subagent,**登录方式和执行纪律全部写进 runbook 文件**,不写进 prompt
(见 `RUNBOOK-template.md`)。prompt 里只说:cd 到哪、读哪个 runbook、负责哪个分片文件、交付什么格式。

这样做的理由:登录链路知识不该占我的上下文,而且下次换人换机器只改 runbook。

### 并发上限
**最多 2 路。** 2026-08-28 实测 4 路并行时本机堆了约 80 个 relay 长连接,
5 台出现 `Connection timed out during banner exchange`。relay 网关是共享瓶颈,
不同节点也会互相影响。

⚠️ **这条只限制"机器数",不限制"机内并行度"。** 一条 ssh 进去起 M 个 pytest 进程,
relay 只算一条连接 —— 所以**扩产能优先往机内加**(见上面「机内并行」),
而不是想办法多连机器。HTTP 隧道也绕不过这条(隧道本身就是一条 ssh)。
瓶颈**不在远端机器数量**,在**本机 → relay 网关**这一跳。
所以池子里有多少台可用是一回事,**我能同时驱动多少台是另一回事** ——
不要把"池子有 20 台能用"直接当成"能同时跑 20 路"。

出路的方向是**把"常驻连接数"和"在跑机器数"解耦**(均未验证):
①下发即断:`nohup` 启动远端脚本后立刻断开,机器在跑但不占连接;
只在**轮询状态时**才连,并发压到 ≤2 条 —— 这样在跑的机器数可以远大于连接数;
②状态用文件/网盘回收,而不是保持 ssh 长连接读 stdout;
③首批错开首连认证,避免同时首连。
**在这条解决之前,不许按"池子里所有机器同时铺开"设计 P3** —— 会整片断在 banner exchange。

### 长连接
`ControlMaster auto` + `ControlPersist 8h`,socket 在 `~/.ssh/sessions/`。
**relay 指纹认证是 per-host 的,N 台就是 N 次首连认证,省不掉**;
长连接省的是同一台机器上后续命令的重连(实测 12s+ → ~0.9s)。
夜间任务要注意 8h 窗口:凌晨建的连接白天可能已过期。

### 审计
每个执行者有**自己的 run 目录**,按 `HANDBACK-schema.md` 的布局
交付:`campaigns/<战役名>/runs/<时间戳>-<机器>-<任务>/{PROMPT.md, handback.md, run.log, 脚本, fetch.err}`。
**一次派发一个新目录,不复用**(隔离靠路径,见 `HANDBACK-schema.md`)。
主 agent 收齐后汇总 `campaigns/<战役名>/INDEX.md`,
**缺哪份要点出来**,不能用"整体成功"盖过去。
摘要级 run.log 要**拉回本机**并双端 md5 比对,让用户不必登机器就能翻。
用户要 review 每一条实际下发的远端命令 —— 这是硬要求,不是可选项。
