# P2:定分片

**什么时候读**:要决定今晚跑几片、每片多大、开几个并行的时候。

**前置**:P1 必须已经拿到真实单文件耗时,否则分片是拍脑袋。


分片依据按优先级:

1. **按硬件档位分** —— 这是硬约束,不是优化。H2(普通 GPU)、H3(CUTLASS SM90+ /
   Blackwell / CK / XPU)必须落到能跑的机器上,否则全是 skip 或 error。
2. **按子特性/测试文件分** —— 天然边界,失败时好定位。
3. **按 P1 耗时配平** —— 让每片时长接近。

## 调度模型:静态分片 + 持久化编排（2026-09-01 修正）

**静态分配只解决“这份测试归哪个 worker”，不等于跑完一轮就停，也不等于不需要编排。**
第一晚确实要保守验证链路；但链路已经真实经历了环境恢复、重试/回退、人工决策、回程副本回收和下一波续跑，不能再用“纯 Bash/JSON 足够”或“每晚靠人判断”作为长期方案。

当前夜间执行分两层：

1. **分片层**：按硬件档位、子特性和实测耗时，把文件静态分给 worker；不做共享队列抢占。
2. **编排层**：本机持久化状态图负责 smoke → freeze_env → run_batch → classify → retry/recover → next_batch → report；worker 完成一份后，在预算和门禁允许时自动领取其固定清单中的下一份。

在状态图实现前，仍可用现有 runner + 静态清单继续跑，但主 agent 不能把“等用户提示再续跑”当作临时常态；每波结束应立即按已知规则续派，状态和产物落盘。

### 编排状态与处置

- `real_gap`：记录兼容性缺口，继续下一文件。
- `env_broken`：进入已知恢复路径并重跑原分片；未知原因进入人工节点。
- `budget_short`：按预算策略重试或标记待续跑。
- `hung` / `machine_lost`：熔断当前 worker，保留证据，后续重新分配。
- `handback_missing`：从远端副本回收；仍无法取证则不得计为完成。
- 到 06:00 停止领取新文件，正在运行的任务按收尾策略处理。

**框架方向**：本机控制面第一候选为 `transitions` + SQLite；LangGraph 是复杂度继续增长时的备选。状态图放白天实现，不能阻塞当晚已经验证的测试链路。

## 机内并行:2 进程已实证安全(2026-08-30 node41 实测)

| 项 | 结果 |
|---|---|
| `PARALLEL_SAFE` | **yes** —— 并行下 `test_multi_kernel.py` 仍是 13/4/2,**逐用例一致,零新增 fail** |
| `CACHE_ISOLATED` | yes,各进程独立 `TORCHINDUCTOR_CACHE_DIR` / `TRITON_CACHE_DIR`(建在 `p1-triton/` 下) |
| 机器 | node41:**208 核**,可用内存 407GB;开工时 CPU 99.3% idle |
| load | 前 3.84 → 后 **36.71** |

**结论:缓存隔离方案有效,2 进程并行安全,可以用。** 这条假设已经压掉。

⚠️ **speedup 数字(1.135x)不可用,不要引用。** 两轮墙钟(2055s / 1810s)都被
`test_combo_kernels.py` 的 1800s timeout 撑满,**测的是 timeout 上限而不是并行收益**。
真实并行收益**仍未测出**,要用两个都能跑完的文件重测。
教训:**基准测试里混入一个撞天花板的样本,整个数字就废了** —— 选样本时先确认它能跑完。

**并行度天花板:执行者给的"最多 2 个"过于保守,不要照抄。**
依据是 load 36.71,但那是**208 核**机器 —— 利用率约 18%,余量很大。
真正的约束是:
- 单个 pytest 进程实测吃 **8~32 核**(注意:`TORCHINDUCTOR_COMPILE_THREADS=1` 也拦不住,
  **功能模拟器本身多线程**)。**所以绝不能按"一进程一核"估算并行度,会严重高估。**
- 按 8~32 核/进程、208 核、留一半给机器主人 → **4~8 进程量级是合理的下一档**。
- 但仍按逐晚加倍来试:2 → 4 → 8,每档都要复核"multi_kernel 是否仍 13/4/2"。

## 机内并行:先做礼貌的邻居,再做快(2026-08-30 用户交代)

用户交代:「发现机器上没有人用卡资源(这个可能有人在 benchmark),虽然我们用模拟器,
占了 CPU 可能也影响别人;如果机器资源空,我们可以开多进程最大化利用机器资源」。

**两个维度的并行,别混为一谈:**

| 维度 | 上限来自 | 现状 |
|---|---|---|
| **跨机并行**(N 台机器) | relay 网关连接数,**实测 4 路即断** | 硬上限,未解决 |
| **机内并行**(单机 M 进程) | 该机 CPU / 内存 / 别人的占用 | **完全没利用,这里有大量余量** |

关键认知:**机内并行不吃 relay 连接** —— 一条 ssh 进去,`docker exec` 里起 M 个进程,
relay 只算一条。所以**扩产能应优先往机内加,而不是往机器数加**。
这是绕过 relay 上限的正确方向(HTTP 隧道不是,隧道本身就是一条 ssh)。

**但机器是共享的,礼貌优先于速度:**
- 镜像默认跑**功能模拟器**,不用真卡 —— 但**吃 CPU 和内存**。
  「我们不用卡所以不影响别人」是**错的**:别人在 benchmark 时,我们抢满 CPU 会污染他的数据。
- 派 agent 前必须**先量该机的实际空闲**,而不是按标称核数算:
  `nproc`、`uptime` 的 load average、`free -g`、`top -bn1` 看谁在跑、`nvidia-smi`/XPU 工具看有没有人占卡。
  **有人在跑 benchmark(卡被占 / load 已高)→ 该机降级或跳过,不要挤进去。**
- 留余量,不要打满:**并行度按"空闲核数"算,并留出一部分给机器主人**。
  宁可少开两个进程,也不要成为那个把别人 benchmark 搞脏的人。
- 每个 agent 必须能**报出它实际用了多少并行度、以及当时的 load** —— 否则事后无法判断
  某片耗时异常是我们自己挤爆了,还是环境本身慢。

**并行怎么落地(不许造调度器,沿用静态预分配):**
- 容器**没有 pytest-xdist**,不要指望 `-n`。并行 = **同一容器内起 M 个独立 pytest 进程,
  各跑不同的测试文件**,输出写各自的日志。
- 文件级切分即可,不要拆到用例级 —— 简单、可复现、日志不混。
- ⚠️ **多进程共享 inductor/triton 编译缓存有互踩风险**:必须给每个进程独立的
  `TORCHINDUCTOR_CACHE_DIR` / `TRITON_CACHE_DIR`(各自子目录),否则缓存竞争会制造假 fail。
  这一条**没有实测过,第一次开多进程时必须专门验证**。
- 仍然是"一实例一 agent",只是**那个 agent 内部并行**;不需要中央协调。

**节奏(不许跳)**:第一晚**单进程**,只证明链路能跑;
先把 4 vs 13 那种不确定性清掉,再谈并行 —— 否则并行只会把不确定性乘以 M。
并行度也按"逐晚加倍"来试:1 → 2 → 4,每次看耗时是否线性下降、有没有新增 fail。
**如果并行后出现单进程没有的 fail,立刻退回单进程**并记录 —— 那是我们自己制造的假缺口,
会污染兼容性清单(见 SKILL.md 开头的大目标判读口径)。

**机器会越来越多**(用户明确会继续放资源)。所以池子的形态是:
机器数 × 机内并行度,两个都可调;**优先加机内并行度**(不吃 relay),
机器数受 relay 4 路限制,除非那条限制被解掉。

**关于"agent 自己判断"的三级升级(用户明确):**

```
agent 遇到问题 → 自己能判断的,自己处理并记录
              → 判断不了 → 找我
              → 我判断不了 → 找你
```

这条很重要:**不要求 agent 遇事即停、也不要求它硬扛。** 它有自主判断权,
边界是"判断不了就上报",而不是"什么都上报"或"什么都自己扛"。
我同理:我判断不了就找你,不自己编一个解释糊过去。

**加倍的节奏是这套设计的核心**:规模不是一次算出来的,是**一晚一晚试出来的**。
所以第一晚的目标不是产出数据量,是**证明这条链能跑起来**。


## 排期反推(P2 定分片时就要算)
工作日可用窗口 = **7 小时**(23:00→06:00)。这个数用来决定**分片切多小**
(小到能频繁回收、好续投),**不是用来决定"总量能不能一晚跑完"** ——
跑不完是常态,没跑完的下一晚继续,见上面「静态预分配 + 逐晚加倍」。
**不许为了"一晚跑完"去砍测试范围**,也不许靠"拖到白天"或"提前到 23:00 前"补。
周末窗口大得多,大批量优先排周末。
