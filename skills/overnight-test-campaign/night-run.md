# P3:夜间无人值守铺开

**什么时候读**:分片方案已定,要真的让它在夜里跑起来的时候。

**前置**:`blockers.md` 里的卡点必须已解决 —— 没解决不许铺开。

## 夜间无人值守:我替用户拍板的授权与边界(2026-08-30 用户明确授权)

用户原话:「半夜跑的话大概我睡了,所以你要尽量都能回答,你可以搜索你的整个记忆包括 git history
等,因为你的信息比 subagent 多,如果你回答不了,就退出吧,白天告诉我」。

**前提:我确实比执行者知道得多。** 执行者无记忆、只看一份 PROMPT;我有全部记忆、
skill 全文、`git -C "$MEMORY_DIR" log` 里的历次踩坑经过、recall 里的往轮对话。
所以执行者卡住时,**默认假设答案在我手上,先查再说"不知道"**。

收到 `NEEDS_DECISION.md` 后的固定动作(**顺序不许跳**):
1. 只读 `NEEDS_DECISION.md`(别 `cat` 整个目录)—— 它卡在哪、候选是什么、缺什么信息。
2. **查我自己的记忆**,按这个顺序:
   `grep -r` 本 skill 全部 md(`pitfalls.md` / `blockers.md` / `boundaries.md` / `machines.md`)
   → `git -C "$MEMORY_DIR" log --oneline` 和 `git log -p` 找当初为什么这么定
   → 必要时派 recall 子代理翻往轮对话。
   **绝大多数夜间卡点是白天已经解过的**(例:环境不闭环 = 漏 `TRITON_ENABLE_XCN_BACKEND=true`;
   用例整片 skip = 拿 `torch.xpu.is_available()` 当门禁)。
3. 拿定主意就写 `<run_dir>/DECISION.md`,给**可直接执行的命令或明确取舍**,不要给"你考虑一下"。

**能自己拍的**(有记忆依据、不越边界、可逆):
换端口/换目录名、调 pytest 参数、加环境变量、重跑取证、放弃某个用例继续跑其余、
选另一台已在池子里的机器、判定某个 fail 是已知基线内的。

**必须停下等白天的**(写 `MORNING-ESCALATION.md` 然后退出,不许自行放行):
要改仓库源码 / 要改容器或宿主机配置 / 要碰别人的目录或进程 / 要装卸包或换镜像 /
要动 `/klxlake` / 需要用户的业务判断(比如"这个 fail 算不算可接受") /
凭据或权限相关 / **任何我查完记忆仍然拿不准的事**。

**硬规则:拿不准就退出,不许猜。**
夜里瞎放行的代价是一整晚白跑 + 一份不可信的报告 —— 比"少跑一个用例、早上问一句"贵得多。
退出时必须留下 `MORNING-ESCALATION.md`:卡在哪、我查了什么、为什么不敢拍、
白天需要用户回答的**那一个具体问题**。早上第一句先报这个,别埋在报告里。

## 我在这套里做什么

| 谁 | 管什么 |
|---|---|
| **每个 agent(一实例一个)** | 拿到自己那份测试,循环跑,自己判断问题,判断不了上报 |
| **远端脚本 / 命令** | 单条不越界:`timeout`、日志落盘、标 `TRUNCATED` |
| **我** | 筛池子、静态分配、**定每晚加不加倍**、收上报、判断红是环境还是真 bug、汇报 |
| **你** | 我判断不了的时候拍板 |

**❌ 已作废的说法**(我提过,被否了,不要再提):
"由我在上下文里维护一个待跑分片队列"、"按回收速度手工动态续投"、"租约到期自动退回"。
真正的教训是：**先把一个实例一个测试跑通，再谈规模；跨轮次状态不能靠我记忆。**

这不否定将持久化状态图用于已经实证出现的多分支编排。当前夜间战役已出现环境恢复、失败分类/重试/熔断、回程回收、续跑和人工决策节点；白天可在本机控制面实现 LangGraph 工作流。需要 LLM 判断未知失败时，采用 `langgraph` + `langchain` + `langchain-openai`，LLM 只负责结构化分类，不能直接执行 shell；这些依赖不得装进 M300 被测容器。夜间窗口内不临时改控制面。

## 机器资源是借来的:窗口与硬性收工(2026-08-30 用户明确)

这些机器**白天是别人干活用的**。我们只在**夜间和周末**蹭空闲资源,所以窗口不是建议,是纪律。

## 窗口
| 时段 | 可用 |
|---|---|
| 工作日 夜间(**23:00** → 次日 **06:00**) | 可用 |
| 周末 全天 | 可用 |
| 工作日 其余时间(06:00 → 23:00) | **禁止铺开** |

⚠️ 工作日窗口只有 **7 小时**,不是 10 小时。**23:00 之前不许启动** ——
别人可能还在用机器,晚上早些时候占卡跟白天占卡一样是事故。

## 硬性收工:早 06:00 必停,跑没跑完都停
**到点强制结束,不允许"就快跑完了再等等"。** 白天占着卡影响别人干活,
比少拿一片数据严重得多。

实现方式(**两层,缺一不可**):
1. **每条测试命令自带 `timeout`**,时长按"距 06:00 还剩多少"算,不要写死一个大数。
   `timeout` 到点会杀掉 pytest,已跑完的用例结果仍在日志里。
2. **总闸看墙钟**:分片循环每跑完一片就查一次当前时间,
   `≥ 06:00` 就**不再启动下一片**,直接收尾写 handback。
   (只靠单条 timeout 不够:最后一片可能 05:59 才启动。)

收工时必须**保住已完成的部分**:handback 里写清
`跑完哪几片 / 哪片被强杀在哪个用例 / 哪几片压根没启动`。
**被截断的分片要标 `TRUNCATED`,不许当成 failed 统计**——
两者含义完全不同,混在一起会把"没跑"误读成"跑挂了"。


## 跨零点的 relay 指纹(2026-08-30 实证踩坑)
relay 指纹**按天失效**。2026-08-30 01:46 的 P1 基线就是这么断的:
`Connection timed out during banner exchange`,16 个文件全部 `UNAVAILABLE`。
**夜间战役必然跨零点**,所以这是整套流程的硬风险,不是偶发。
P3 铺开前必须先定跨天续认证的办法(候选:零点后再启动、睡前解锁看能否覆盖整夜、
查 relay 有无长效凭据),**没定就不许安排跨零点的无人值守任务**。


## 触发
用 `letta cron` 建定时任务(加载 `scheduling-tasks` 技能拿准确 flag,别背)。
一次战役用**一次性 cron**,不要建成 recurring——跑砸了会每晚重复烧机器。

## 派发命令(2026-08-30 实测定型)

```bash
RUN_DIR=campaigns/<战役名>/runs/$(date +%Y%m%d-%H%M)-<机器>-<任务>
mkdir -p "$RUN_DIR"
nohup ducx exec -m gpt-5.6-terra \
  -c model_provider=oneapi -c model_reasoning_effort=high \
  --skip-git-repo-check -s danger-full-access \
  "$(cat "$RUN_DIR/PROMPT.md")" > "$RUN_DIR/ducx.log" 2>&1 &
```
**三个参数一个都不能省**(理由见 [[system/human/preferences/token-efficiency.md]]):
`-m` 挑模型、`model_provider=oneapi` 否则 fallback 到 openai 死循环重连、
`model_reasoning_effort=high` 否则被 config 里的 `low` 拖成低推理。
夜间战役用 **`gpt-5.6-terra`**(最强);轻量汇总用 `sol` 省额度。
`ducx.log` 是它的 stdout,**我不读**,只读它写的 `handback.md`。

## 委托
给每片起一个 subagent,**登录方式和执行纪律全部写进 runbook 文件**,不写进 prompt
(见 `RUNBOOK-template.md`)。prompt 里只说:cd 到哪、读哪个 runbook、负责哪个分片文件、交付什么格式。

这样做的理由:登录链路知识不该占我的上下文,而且下次换人换机器只改 runbook。


## 审计
每个执行者有**自己的 run 目录**,按 `HANDBACK-schema.md` 的布局
交付:`campaigns/<战役名>/runs/<时间戳>-<机器>-<任务>/{PROMPT.md, handback.md, run.log, 脚本, fetch.err}`。
**一次派发一个新目录,不复用**(隔离靠路径,见 `HANDBACK-schema.md`)。
主 agent 收齐后汇总 `campaigns/<战役名>/INDEX.md`,
**缺哪份要点出来**,不能用"整体成功"盖过去。
摘要级 run.log 要**拉回本机**并双端 md5 比对,让用户不必登机器就能翻。
用户要 review 每一条实际下发的远端命令 —— 这是硬要求,不是可选项。

## 早上的交付
`campaigns/<名字>/REPORT-<日期>.md`,必须包含:
- 与 P1 基线的 pass/fail 对比(**新增的 fail 是唯一真正重要的信息**)
- 每片实际耗时 vs 估算
- 环境搭建过程中的意外(缺包、拉镜像失败、盘满)
- 明确的下一步建议
